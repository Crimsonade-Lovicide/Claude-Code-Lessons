Claude Code · advanced operator's guide

Stop prompting. Start configuring the harness.

Beginners talk to Claude Code. Experts shape the environment it works in: what it knows, what it may do without asking, what it must always do, and how many copies of it run at once. This guide walks those layers from the inside out. Each one ends with a drill you can tick off.

LAYER 0

The mental model that makes everything else click

Claude Code is a loop: read context, pick a tool, act, observe, repeat. Every advanced feature controls one of four things in that loop.

ContextWhat's in the window. It is the scarce resource. Quality drops as the window fills with stale debugging, unused tool definitions and long files. CLAUDE.md, skills, subagents and /compact all exist to manage it.
AuthorityWhat Claude may do without asking. Permission rules, modes and the sandbox. More authority means fewer interruptions and longer unattended runs.
GuaranteesWhat happens every time, whatever the model decides. Instructions are probabilistic; hooks are deterministic. If "usually" isn't good enough, it's a hook.
ConcurrencyHow many loops run at once. Subagents, worktrees, background tasks, cloud sessions, workflows, headless runs in CI.

PracticeWhen a session goes badly, diagnose it with these four words before you rewrite the prompt. Most failures are context failures (it forgot, or was drowning) or verification failures (it had no way to know it was wrong).

The second idea: give Claude a way to check its own work. A test suite, a typecheck, a linter, a screenshot. A model with a feedback signal iterates to correct. A model without one stops when the code merely looks right.

DECISION TABLE

Which extension point?

The most common expert mistake is putting a thing in the wrong layer: a must-always rule in CLAUDE.md, or a 400-line procedure loaded every session.

You wantUseWhy this layer
Claude to always know a command, convention or gotchaCLAUDE.mdLoaded every session. Every line is paid for on every turn, so keep it short.
A rule that only matters for some files.claude/rules/Path-scoped, so it loads only when Claude touches matching files.
A repeatable procedure you trigger by nameSkillOnly the short description sits in context until invoked. Becomes /name.
Research or review that would flood your contextSubagentRuns in its own window and hands back a summary. Your main thread stays clean.
Something that must happen every time, no exceptionsHookRuns as code, outside the model. It can't forget or decide to skip.
Stop dangerous actionsDeny rules + sandboxRules stop the obvious; the sandbox is the real boundary. Hooks cover patterns rules can't express.
Reach an outside system (DB, Sentry, CRM, browser)MCP serverGives Claude typed tools for that system instead of you pasting data in.
Run with nobody watchingclaude -p / Action / routineHeadless mode, GitHub Actions, scheduled sessions.
Many independent tasks at onceWorktrees / cloud / workflowSeparate checkouts so parallel agents don't trample each other's files.
Ship all of the above to a team or another repoPluginOne installable bundle of skills, agents, hooks and MCP config.
LAYER 1

Session craft

Before any configuration, the biggest gains come from how you run a single session.

Plan before code on anything non-trivial

DocumentedPress Shift+Tab to cycle permission modes, including plan mode, where Claude reads and proposes but can't edit. Use it whenever the change touches more than a couple of files or you aren't sure of the approach.

PracticeThe strongest pattern for big features is interview → spec → fresh session:

prompt
I want to add conflict-of-interest checks to client intake.
Interview me with questions one at a time until you understand the
requirements, edge cases and constraints. Then write the spec to
docs/specs/conflict-check.md. Don't write any code yet.

Then /clear and start a new session: "Implement docs/specs/conflict-check.md. Run the tests after each step." The implementer gets a clean window and a precise target instead of a transcript full of back-and-forth.

Control effort and model per task

Documented/model switches models mid-session. /effort sets reasoning depth (low through max). /fast toggles fast mode, which is faster output on the same model. Use low effort for renames and boilerplate and high effort for debugging and architecture. Thinking you don't need costs time and tokens.

Feed context precisely

  • @src/lib/llm.ts pulls a file in directly, so Claude doesn't have to search for it.
  • !npm test runs a shell command yourself and puts its output in the conversation.
  • Paste screenshots (Ctrl+V) or drag images in. A mockup or an error screenshot beats a paragraph describing it.
  • Pipe data in: cat error.log | claude.

Recover instead of arguing

DocumentedEsc interrupts. Esc Esc (or /rewind) rewinds the conversation and/or code to an earlier checkpoint. claude -c continues the last session; claude -r picks one to resume.

PracticeIf you've corrected Claude twice on the same thing, stop. The wrong attempts are now in context and pull it back toward the mistake. Rewind to before the first attempt and rewrite the prompt with what you learned. This is the single highest-ROI habit in this guide.

Watch the meter

/context shows what fills the window: system prompt, MCP tool definitions, memory files, conversation. /compact focus on the API decisions; drop the debugging summarizes with your priorities. /clear between unrelated tasks. /usage shows spend and limits.

LAYER 2

Memory: CLAUDE.md and rules

CLAUDE.md is the onboarding doc a new senior engineer would need on day one, written for a reader with perfect recall and no common sense about your project.

DocumentedClaude loads, in layers: your user file ~/.claude/CLAUDE.md (all projects), the project's CLAUDE.md (commit it), and CLAUDE.md files in subdirectories, which load when Claude works in that directory. @path imports another file. /init drafts one from your codebase. /memory opens the files for editing. Claude also keeps an auto memory of things it learns, which /memory shows you.

CLAUDE.md · illustrative; swap in your real commands
# Intake App

## Commands
- Dev server: `npm run dev`
- Single test file: `npx vitest run path/to/file.test.ts`
- Typecheck: `npm run typecheck` (run before every commit)

## Rules
- Never log client names or matter details. Use matter IDs.
- All LLM calls go through `src/lib/llm.ts`. Never import a provider SDK elsewhere.
- Validate every server action's input with zod.

## Gotchas
- DB types are generated. After a migration run `npm run gen:types`; never hand-edit.
- Tests hit a local Supabase. Start it with `supabase start` first.

@docs/architecture.md

Path-scoped rules

VerifyFiles in .claude/rules/ can declare which paths they apply to, so API conventions load only when Claude edits API code:

.claude/rules/api.md
---
paths:
  - "src/app/api/**"
---
- Every route returns { data } or { error, code }. Never throw to the client.
- Rate-limit public routes with `withRateLimit()`.

What belongs in it

PracticeInclude what Claude can't infer from the code: exact commands, non-obvious conventions, traps that burned you, and where things live. Leave out what it can read for itself (the stack is in package.json), generic advice ("write clean code"), and long docs it only sometimes needs (import those, or make them skills). Aim for under ~150 lines. Each time Claude repeats a mistake, ask whether one line in CLAUDE.md would have prevented it. If so, have Claude add it.

Words like "IMPORTANT" or "NEVER" do raise compliance. If something matters enough to need them every time, it probably belongs in a hook.

LAYER 3

Skills: procedures on demand

A skill is a folder holding a SKILL.md plus any scripts or references. Only its name and description stay in context until it's used, so you can have dozens at almost no cost.

DocumentedSkills live in .claude/skills/<name>/SKILL.md (project) or ~/.claude/skills/ (personal). Each becomes /<name>. Custom slash commands have been folded into skills; old .claude/commands/*.md files still work. Useful frontmatter: description (when to use it, which drives auto-invocation), disable-model-invocation: true (only you can trigger it), allowed-tools (pre-approved tools while it runs), model, and context: fork (run it in an isolated subagent). In the body, $ARGUMENTS or $1 insert your arguments, and !`cmd` runs a shell command first and inlines its output.

.claude/skills/ship/SKILL.md
---
name: ship
description: Typecheck, test, commit and open a draft PR for the current change.
disable-model-invocation: true
allowed-tools: Bash(npm run:*), Bash(git:*), Bash(gh pr create:*)
---
Branch: !`git branch --show-current`
Changes: !`git status --short`

1. Run `npm run typecheck` and `npm test`. On failure, fix and rerun.
   After 3 failed attempts, stop and report what's blocking.
2. Write a conventional commit message from the diff and commit.
3. Push, then `gh pr create --draft` with: what changed, why, how it was tested.

Extra instructions: $ARGUMENTS

Now /ship skip the e2e suite is one command. A skill can bundle scripts too: put scripts/check-citations.py next to SKILL.md and tell Claude to run it. Code is more reliable than prose for anything mechanical.

PracticeWrite the description for the model, not for people: say when to use the skill, including the phrases you'd naturally type. A vague description is the usual reason a skill never auto-triggers. Make side-effecting skills (deploy, send, publish) disable-model-invocation so Claude can't decide to run them itself.

Built-ins worth knowing: /code-review, /security-review, /simplify, /init, /loop, and /fewer-permission-prompts, which reads your history and proposes an allowlist.

LAYER 4

Subagents: protect the main context

The point of a subagent is less specialization than context isolation. It can read 40 files and return 20 lines, leaving your main window clean.

DocumentedBuilt-ins include Explore (read-only codebase search), Plan and general-purpose. Custom agents are Markdown files in .claude/agents/ (or ~/.claude/agents/). Key frontmatter: name, description, tools (allowlist; it inherits everything if you omit it), model, permissionMode, skills. /agents manages them.

.claude/agents/reviewer.md
---
name: reviewer
description: Skeptical senior reviewer. Use after any non-trivial change and
  before committing. Reports problems; never edits files.
tools: Read, Grep, Glob, Bash
model: sonnet
---
You are reviewing someone else's diff, and you assume it has a bug.
Run `git diff main...HEAD`. Check for: logic errors, unhandled edge cases,
leaked client data, missing input validation, and untested branches.

For each finding give file:line, a concrete failure scenario, and the fix.
Rank by severity. If nothing is wrong, say so in one line. Don't pad.

Call it explicitly ("have the reviewer check this") or let the description route to it.

PracticeThree patterns are worth having:

  • Fresh-eyes review. The agent that wrote the code is biased toward it. A reviewer with no memory of writing it catches more.
  • Parallel research. "Use 3 subagents in parallel: one maps the auth flow, one finds every caller of billMatter(), one reads the Stripe webhook handler. Summarize." Three windows' worth of reading, one window's worth of result.
  • Cheap grunt work. Put model: haiku on agents that only search or summarize.

Restrict tools deliberately. A read-only reviewer can't "helpfully" rewrite your code.

LAYER 5

Hooks: guarantees, not requests

A hook is a command the harness runs at a lifecycle event. It gets the event as JSON on stdin and can approve, block or add context.

DocumentedHooks are configured in settings files under "hooks", grouped by event, with a matcher on tool names. Core events: PreToolUse (can block), PostToolUse, UserPromptSubmit, Stop, SubagentStop, SessionStart, SessionEnd, PreCompact, Notification and PermissionRequest. Exit code 0 means proceed. Exit code 2 blocks the action and sends your stderr to Claude as feedback. $CLAUDE_PROJECT_DIR points at the repo root. /hooks shows what's active.

VerifyThe event list keeps growing, and newer builds add hook types beyond command (such as prompt and http hooks). Check /hooks in your version.

Three hooks worth having

.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command",
          "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write --ignore-unknown" }] }
    ],
    "PreToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command",
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-paths.sh" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
          "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/require-green.sh" }] }
    ]
  }
}
.claude/hooks/protect-paths.sh
#!/usr/bin/env bash
path=$(jq -r '.tool_input.file_path // empty')
case "$path" in
  *.env|*.env.*|*/migrations/applied/*)
    echo "Blocked: $path is protected. Ask the user to change it." >&2
    exit 2 ;;
esac
exit 0
.claude/hooks/require-green.sh · Claude can't say "done" while tests fail
#!/usr/bin/env bash
input=$(cat)
# Prevent an infinite loop: if we already blocked once this turn, let it stop.
[ "$(echo "$input" | jq -r '.stop_hook_active')" = "true" ] && exit 0

if ! npm test --silent > /tmp/claude-tests.log 2>&1; then
  echo "Tests are failing. Fix them before finishing:" >&2
  tail -n 30 /tmp/claude-tests.log >&2
  exit 2
fi
exit 0

Remember chmod +x .claude/hooks/*.sh. Other high-value hooks: a SessionStart hook that installs dependencies in cloud sessions (the built-in session-start-hook skill sets one up), and a Notification hook that pings your phone or desktop when Claude needs you.

Hooks run with your full user permissions, automatically. Read any hook before you install one from a plugin or another repo, the same way you'd read a shell script you were about to pipe into bash.

PracticeKeep hooks fast. A Stop hook running a five-minute suite after every turn will make you hate it. Point it at the fast unit tests and leave e2e for CI.

LAYER 6

Permissions, modes and the sandbox

Every permission prompt is a context switch for you. Experts approve the safe 90% in advance and spend their attention on the 10% that matters.

DocumentedSettings files layer like this: managed (organization) policy, then ~/.claude/settings.json (you), .claude/settings.json (team, committed), .claude/settings.local.json (you, this repo, gitignored), and CLI flags. Rules come in allow, ask and deny, and deny wins. Modes: default, acceptEdits, plan, auto (a classifier approves routine actions), dontAsk, and bypassPermissions.

.claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)", "Bash(npm run typecheck)", "Bash(npm run lint:*)",
      "Bash(git status)", "Bash(git diff:*)", "Bash(git log:*)"
    ],
    "ask":  [ "Bash(git push:*)", "Bash(supabase db:*)" ],
    "deny": [ "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)" ]
  }
}

Bash rules match command prefixes. They are not a security boundary. Denying curl does nothing against python -c "import urllib…". For real isolation use the sandbox (/sandbox), which restricts filesystem and network at the OS level, or run in a container or cloud session. Use bypassPermissions only inside something disposable.

PracticeRun /fewer-permission-prompts after a week of normal use. It mines your actual approvals and proposes rules, which beats guessing. Commit read-only, team-safe rules to .claude/settings.json and keep personal ones in settings.local.json. /permissions lets you review everything in one place.

LAYER 7

MCP: give Claude hands outside the repo

MCP servers expose external systems as tools: your database, error tracker, browser, CRM, design files.

DocumentedAdd servers with claude mcp add. Scopes: local (you, this project; the default), project (written to .mcp.json and committed for the team), and user (you, everywhere). .mcp.json supports ${VAR} and ${VAR:-default} expansion, so secrets stay in your environment. /mcp shows status and handles OAuth.

terminal
# Remote server over HTTP (OAuth handled in /mcp)
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

# Local stdio server, shared with the team via .mcp.json
claude mcp add --scope project --transport stdio playwright -- npx @playwright/mcp@latest

claude mcp list

With Playwright connected, Claude can open your running app, click through a flow and screenshot it. That turns "it compiles" into "I watched it work", the verification signal from Layer 0. For UI work it's the single most useful server.

PracticeEvery connected server adds tool definitions. Recent versions defer loading most of them until needed, but connect what you use, not everything you can, and check /context after adding a big one. You already have many connectors on claude.ai (Supabase, Vercel, HubSpot, Gmail, Notion and more). In this cloud environment they're available, so "check Vercel's runtime logs for the last deploy and correlate with Supabase errors" is a single prompt.

LAYER 8

Parallelism: many Claudes, no collisions

Once one session is reliable, your throughput is limited by how many you can run and review at once. The constraint is file collisions, and git worktrees solve it.

Worktrees

terminal
# Built in: a new session in an isolated worktree
claude --worktree billing-refactor

# Or by hand, which works everywhere
git worktree add ../app-billing -b feat/billing-refactor
cd ../app-billing && claude

Each worktree is a separate checkout on its own branch: one agent refactors billing while another writes tests for intake, with no shared files.

Background and cloud

  • DocumentedLong-running commands (dev servers, test watchers) can run in the background while Claude keeps working. Ctrl+B backgrounds one, and /tasks lists them.
  • DocumentedCloud sessions (claude.ai/code, the desktop and mobile apps, or started from the CLI) run in an isolated container. Hand off a task, close your laptop, review the PR later. --teleport pulls a cloud session down into your terminal.
  • VerifyThe CLI flag that starts a cloud session has been renamed between versions. Check claude --help.

Workflows: orchestration at scale

DocumentedA workflow is a script that fans work out across many subagents with deterministic structure: review every changed file on five dimensions, then adversarially verify each finding. You opt in by saying "use a workflow" or including the word ultracode; /workflows shows live progress.

PracticeWorkflows can spawn dozens of agents and burn tokens fast. They pay off for wide, parallelizable work like audits, migrations across many files and multi-angle research. For a single feature they're overkill. Your bottleneck will be review, not generation: run only as many parallel streams as you can actually read.

LAYER 9

Automation: Claude without you

claude -p turns Claude Code into a Unix command. Anything you can script, you can now hand to an agent.

DocumentedKey flags: -p (print mode, non-interactive), --output-format text|json|stream-json, --allowedTools / --disallowedTools, --permission-mode, --max-turns, --model, --append-system-prompt, --mcp-config, --add-dir, and -c / -r to continue or resume.

terminal
# Structured output for scripts
claude -p "Summarize the last 10 commits as release notes" --output-format json | jq -r '.result'

# Read-only review piped from git
git diff main | claude -p "List security issues in this diff. Findings only." \
  --allowedTools "Read,Grep,Glob"

# Fan out a mechanical migration, 4 at a time
git ls-files 'src/legacy/*.js' | xargs -P 4 -I{} claude -p \
  "Convert {} to TypeScript with identical behavior. Run npx tsc --noEmit on it." \
  --allowedTools "Read,Write,Edit,Bash(npx tsc:*)" --max-turns 15

GitHub

DocumentedRun /install-github-app to install the app and generate a workflow. After that, @claude in any issue or PR comment starts a run. The workflow it writes looks roughly like this:

.github/workflows/claude.yml
name: Claude
on:
  issue_comment: { types: [created] }
  pull_request_review_comment: { types: [created] }
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions: { contents: write, pull-requests: write, issues: write, id-token: write }
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}

Add a prompt: input and a schedule: trigger and you have a nightly job: triage new issues, fix dependency alerts, update docs.

Recurring and scheduled

/loop 10m check the deploy and tell me if error rate rises repeats a prompt inside a session. Routines are scheduled cloud sessions that fire on a cron schedule without your laptop. Ask Claude to set one up ("every weekday at 8:50, review open PRs and summarize what needs me") or manage them at claude.ai/code.

LAYER 10

Plugins and the Agent SDK

Plugins: package your setup

Once your skills, agents and hooks work, a plugin makes them one install in every repo and for every teammate.

plugin layout
ai-esquire-dev/
├── .claude-plugin/plugin.json   # { "name": "ai-esquire-dev", "version": "0.1.0", "description": "…" }
├── skills/ship/SKILL.md
├── agents/reviewer.md
├── hooks/hooks.json
└── .mcp.json

DocumentedPut it in a git repo with a marketplace manifest. Others then run /plugin marketplace add owner/repo and /plugin install ai-esquire-dev@<marketplace>. Use /plugin to browse what's installed or available.

Agent SDK: build your own agents

DocumentedThe same loop that powers Claude Code, as a library: @anthropic-ai/claude-agent-sdk (TypeScript) and claude-agent-sdk (Python). Reach for it when the agent is the product, such as an intake agent that reads documents and fills your CRM, rather than a tool you use while coding.

agent.ts
import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const msg of query({
  prompt: "Find every exported function in src/ with no test coverage.",
  options: { allowedTools: ["Read", "Grep", "Glob"], maxTurns: 10 },
})) {
  if (msg.type === "result" && msg.subtype === "success") console.log(msg.result);
}

EXECUTION PLAN

A four-week path to expert

Ordered by leverage. Each week builds on the one before. Expect roughly 2 to 3 hours of deliberate practice per week on top of your real work, using your real repos.

Week 1 · Context

  • Prune CLAUDE.md in your main repo
  • Plan mode and the interview → spec habit
  • Rewind instead of correcting
  • /context, /compact, /clear
Done when: you rewind more often than you re-explain.

Week 2 · Reuse

  • Two skills from your most-repeated prompts
  • The reviewer subagent
  • Deny rules, then /fewer-permission-prompts
Done when: permission prompts are down ~70% and /ship is muscle memory.

Week 3 · Guarantees

  • Formatter hook and Stop-on-red hook
  • Playwright MCP for visual verification
  • A Notification hook to your phone
Done when: Claude never reports done on a failing test.

Week 4 · Scale

  • Two worktrees plus one cloud session in parallel
  • GitHub app and @claude on issues
  • Package everything as a plugin
Done when: you merge work you didn't sit and watch being written.

Staying current. Claude Code ships changes almost weekly.
